## 2. 실제 근본 원인과 미확정 사항

확인한 실행 경합: 운영 주기 사이클은 최대 90초 budget의 분석·관측·진입 작업을 전역 account lease 안에서 수행합니다. lease TTL은 150초입니다. BUY도 같은 lease를 사용합니다. claim은 lease 뒤에 있지만, 사이클 도중 생성된 승인 BUY가 기다리며 유효창을 소진할 수 있습니다. GPT 재검토와 X1 관측 루프도 이 범위에 있습니다.

확인한 crash 위험: 실제 `leader20_execution_claim(uuid,uuid,bigint)`는 만료된 ORDER_SUBMITTING을 다시 claim했습니다. v185/migration은 이 상태와 이미 주문 identity가 존재하는 요청을 UNKNOWN으로 보내며, SUBMITTING → READY도 차단합니다. 이 경로로 실제 중복 주문이 발생했다는 증거는 아직 없습니다. 확인한 것은 위험한 상태 전이입니다.

확인한 별도 backlog: 닫힌 포지션 7건의 native stop은 거래소에 없지만 원장에 CANCEL_PENDING으로 남았습니다. v184는 명시적인 PRE_SEND 실패만 NOT_SENT로 기록합니다. 과거 budget/abort 오류를 미전송으로 추정하지 않았습니다. 과거 7건은 신선한 complete 거래소 이력, 정확한 SELL trade/receipt 귀속, 기존 정산 완료와 계좌 flat 증거를 모두 요구하는 별도 fenced transaction으로 정리했습니다.

DB 재시작 원인은 미확정입니다. 실제 postmaster 시작은 05:36:11.400746 UTC / 14:36:11.400746 KST, 06:06:03.502642 UTC / 15:06:03.502642 KST, 06:35:57.669629 UTC / 15:35:57.669629 KST였습니다. 에이전트가 restart를 실행하지 않았습니다. shutdown/플랫폼 제어 이력과 재시작 직전 자원 시계열을 대조해야 합니다. 반복 간격만으로 원인을 확정하지 않습니다.

## 3. 변경 전·후 실행 구조

현재 운영: GPT FINAL BUY → logged dispatch → pg_net wake 또는 sweeper → 전역 lease → atomic claim → 기존 검증 → durable order intent → 거래소 → same-ID 조회 → 체결/포지션/보호. 주기 분석·관리도 같은 lease를 사용합니다.

현재 적용한 차이: 불명확한 전송 결과는 UNKNOWN으로 보존하고 재진입을 차단합니다. 주기 reconciliation 뒤와 dispatch drain 전에 동일 decision/order/position 증거로 journal을 복구합니다. 부분 체결을 전량 체결로 확정하지 않습니다. 보호 backlog의 proof event는 logged table에 남았습니다.

목표 구조: analysis/AI/capture는 lease 밖, account writer만 주문·취소·청산·보호·상태 확정, 외부 단일 scheduler와 reconciliation-first entry freeze. 준비된 writer/scheduler draft와 실제 production 호출자 연결은 구분합니다. 현재 긴 lease가 제거됐다고 주장하지 않습니다.

## 10. 아직 남은 위험

긴 account lease의 실제 caller 분리, gateway 최종 side-effect fencing, 외부 scheduler의 실제 registry/recovery adapters와 cron cutover, P10 entry retirement, 남는 cron 중첩 측정, 반복 Postgres restart 원인이 남아 있습니다. 기존 닫힌 포지션의 ACCOUNTED cache와 authoritative attribution/receipt를 구분해 추가 검증 중입니다. 모르는 원장을 강제로 settled로 바꾸지 않습니다.

새 SQL guard는 crash 이후 재주문 위험을 줄이는 실제 운영 변경입니다. system dropout가 남아 있으므로 전체 완료라고 선언하지 않습니다. 24시간 미래 지표를 성공으로 쓰지 않습니다.

## 11. rollback 방법

v183/v184 전체 소스와 hash를 보존했습니다. v185 source rollback은 v184 93개를 재배포하되 새 no-resubmit RPC를 유지하는 방식입니다. SQL 안전장치는 v184와도 호환됩니다. unsafe ORDER_SUBMITTING reclaim을 실거래 중 복원하지 않습니다. `DISPATCH-CRASH-ROLLBACK.md`와 `CLOSED-NATIVE-ROLLBACK.md`에 순서와 금지 사항을 기록했습니다.

closed-native proof event와 settled 기록, 경제 원장/PnL을 지우거나 과거 snapshot으로 덮어쓰지 않습니다. 향후 scheduler rollback은 Fly 비활성 확인 → fence 갱신/진행 중 작업 확인 → 정확한 cron backup 복원 순서입니다. 신·구 scheduler를 동시에 켜지 않습니다.
