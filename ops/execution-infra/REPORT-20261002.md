## 2. 실제 근본 원인과 미확정 사항

확인한 코드상 구조: v183의 주기 사이클은 전역 execution lease 안에서 분석·관측·유지보수까지 수행합니다. 소스 TTL은 150초, cycle budget은 90초입니다. BUY 실행도 같은 lease를 사용합니다. 실제 lease 점유 p99와 경합의 실패 기여율은 DB 접근 불가로 측정하지 못했습니다. v183은 이미 lease → dispatch claim 순서를 사용했고, 구형 main은 claim → lease와 10초 대기를 사용했습니다. PR #276에서 운영 소스를 동기화했습니다.

기존 migration은 logged dispatch를 durable source of truth로, pg_net을 wake 경로로 설계합니다. 실제 production relpersistence와 설치된 RPC 정의는 SQL 불가로 다시 확인하지 못했습니다. pg_net queue가 주문 요청의 유일한 저장소였다고 주장하지 않습니다. 저장소의 기존 claim SQL에는 만료된 ORDER_SUBMITTING 재claim 경로가 있어, 새 writer에는 UNKNOWN의 same-ID reconciliation과 재제출 금지를 구현했습니다.

현재 별도 장애: Supabase health의 db/db_postgres_user/rest가 UNHEALTHY, pooler는 ACTIVE_HEALTHY이나 upstream DB 연결 timeout입니다. SQL management API는 HTTP 544, metrics API는 HTTP 500입니다. 02:33 UTC / 11:33 KST 재감사([run 36956185458](https://github.com/sanbital/Trading-booooo/actions/runs/36956185458))에서도 동일 상태입니다. session 5432·transaction 6543 모두 upstream timeout이고 service-role REST 읽기도 timeout입니다. 프로젝트 metadata의 ACTIVE_HEALTHY는 실제 DB readiness 성공을 의미하지 않았습니다. 직접 DB 주소는 IPv6뿐이고 GitHub runner는 IPv6 경로가 없어 NETWORK_UNREACHABLE입니다. 이것을 DB 자체의 직접 TCP 실패로 해석하지 않습니다.

초기 감사의 PGDATABASE 환경변수 사용은 remote host를 선택하지 못했습니다. 해당 초기 direct probe 결과는 원격 연결 증거에서 제외합니다. `--dbname` 수정 후 실제 pooler timeout을 확인했습니다.

## 3. 변경 전·후 실행 구조

현재 운영: GPT 완료 → logged dispatch/pg_net wake → 전역 lease → claim/진입 검증/주문. 주기 분석·관측·관리도 같은 lease를 사용합니다. Fly에는 기존 scan 12초/monitor 2초 타이머가 있습니다.

준비한 변경: logged command outbox → account writer lease → atomic claim → 기존 guard 재검증 → durable SUBMITTING → gateway payload/fence 검사 → same-ID 조회 → 기존 귀속/보호 adapter. UNKNOWN은 재제출하지 않습니다. UNKNOWN 재조회는 backoff하고, 보호/청산을 우선하며, UNKNOWN이 있는 동안 신규 진입을 차단합니다.

복구 pipeline은 readiness → open orders → positions → UNKNOWN reconciliation → fill attribution → protection → capacity 순서로 실행합니다. 긴 작업은 writer lease 밖에서 수행하고, 마지막 DB 완료 구간만 lease를 사용합니다. postmaster/generation/event cursor가 바뀌면 복구 완료를 거부합니다.

새 구조는 비활성 expand 상태입니다. v183의 실제 validation/position attribution/protection 호출자를 새 worker에 연결하는 변경은 아직 완료되지 않았습니다. 따라서 운영의 긴 lease가 제거됐다고 주장하지 않습니다.

## 11. rollback

현재 실제 trading 배포를 바꾸지 않았으므로 기존 v183/Fly 이미지/cron이 rollback 기준입니다. v183/v453/v51/v81 전체 source backup과 실행 중 Fly config를 보존했고 raw 자료는 암호화했습니다. DB cron/settings backup은 불가하여 확보됐다고 주장하지 않습니다.

비활성 expand 코드는 revert해도 기존 실행 경로를 바꾸지 않습니다. 활성화 이후 rollback은 신규 entry freeze → UNKNOWN/SUBMITTING reconciliation/보호 확인 → 새 worker/scheduler 중지 → 정확한 cron backup 복원/기존 writer 복원 순서입니다. 새 scheduler가 살아 있는 동안 기존 cron을 복구하지 않습니다. outbox/history를 지우거나 주문 이후 과거 snapshot으로 원장을 덮어쓰지 않습니다.
